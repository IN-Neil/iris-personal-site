Iris Journey on iPhone

How can the paper-boat journey run on phones with the smallest reliable change? One scene for every screen. Phones see a narrower crop of the same world, not a re-drawn one.

Scene architectureOne Journey and one Stage for all widths. Retire JourneyStacked. No second animation system.
Mobile framingKeep a desktop-like scene aspect (0.9 × height wide) and slide a phone-width window across it using one new keyframe track.
Scroll measurementBase everything on the large viewport (lvh). Progress comes from scrollY and cached sizes. Ignore resizes where only the toolbar height changed.
AcceptanceLayout checks in the Simulator. Smoothness and memory on a physical iPhone. The pass is bounded to 16 checks.
1 · Shared scene architecture

One timeline, one scene, two framings

The timeline in src/lib/journey.ts does not depend on screen size. Its keyframes, scrollBeats, chapterPhases, exampleWindow and sceneState are all functions of a single progress number, and the tests cover them. The desktop assumptions live in a few size values in Journey.tsx and Stage.tsx. So the change is a framing setting, not a new system.

Let CSS choose the framing. The script always writes the same numbers. That means the server HTML is identical for phones and desktops, there is no hydration mismatch, and no first-paint flash. It also removes the duplicate rendering that exists today.

Why a crop and not a portrait re-draw

Stage sizes some sprites by width and others by height. By width: boat 12%, dock 40%, clouds, cliffs. By height: figures 10.3cqh, lighthouse 9.5cqh. On a 393×852 screen the figures render about 300px tall standing on a 54px dock, and the boat is 47px wide. I checked this in the browser. A crop keeps the scene at a desktop-like shape, so every sprite keeps its desktop size relative to the others.

2 · Mobile framing rules

Portrait composition at 393 × 852

Each drawing below comes from a prototype. I injected the crop into the existing static build in the browser and did not edit source. Pixel values are measured from that prototype. The boat, the figures and the lighthouse all stayed in frame.

The rules

  1. Framing switch. Use portrait framing when max-aspect-ratio: 9/10. The scene is max(100vw, 90lvh) wide. It is translated by cropStops and clamped so the scene's edge never shows.
  2. Boat first. At every progress value the boat is completely inside the crop. That becomes a unit test on cropStops × boatXStops, including zoom around the boat pivot.
  3. Copy band. Copy starts at max(92px, safe-top + 76px). It may cross the horizon but must end 16px above the boat's top edge (about 81.5% of height). It is never clipped, never scrolls inside, and never shrinks below the site's current type sizes.
  4. One thing in the sky at a time. Copy, then examples, following the existing chapterPhases and exampleWindow timing, unchanged.
  5. Keep these desktop relationships: figures standing on the dock, the boat on the waterline with its candle lit, one camera zoom (1 → 1.4 → 1), and the lighthouse on its cliffs with the beam sweeping. Text never covers the boat.
  6. Chrome: the route map and brand mark respect env(safe-area-inset-*). The scene itself runs full-bleed under the bars.
  7. Short landscape (max-height: 500px): use wide framing. Place chapter one's copy on the right (as chapters 2–4 already are) so the boat at 28–40% stays clear. Hide the brand mark.

3 · Scroll measurement strategy

Measure against a viewport that never moves

Today, progress is -rect.top / (rect.height − innerHeight), read with getBoundingClientRect() on every frame. On iOS, innerHeight grows and shrinks as the toolbar collapses, so the denominator changes mid-scroll and the boat jumps. Replace it with fixed large-viewport sizes that are measured once.

4 · Rendering performance

What we measured, and what only an iPhone can say

Measured in Chrome with a 393×852 viewport on an Apple-silicon Mac. I scrolled 60 steps of 12px each, at four points on the timeline. These numbers count work. They do not predict iPhone smoothness.

The scene runs 106 CSS animations at once. React re-renders the whole Stage every frame, because progress is state in Journey.

Ranked risks

  1. measured Ninety star spans each get the same opacity write every frame (Stage.tsx:188). Moving it to the parent layer cuts about 75% of per-frame DOM writes. It is cheap, visually identical, and should be done first.
  2. hypothesis · highest stakes Memory from very wide layers. Seven will-change layers at 660% of the scene width. The crop makes the scene 767px wide, so each layer is about 5,060 × 852 CSS px, or about 15,000 × 2,500 device px at 3×. WebKit tiling should back only the visible tiles, but that isn't documented. Failure looks like "A problem repeatedly occurred". Measure in the Layers tab.
  3. hypothesis Full-screen mix-blend-mode: overlay grain forces blending over every changing pixel. Try a baked image at plain opacity and compare.
  4. hypothesis Four wave bands animate background-position on layers several screens wide. That repaints every frame regardless of scroll.
  5. hypothesis filter animations: brightness twinkle on 95 spans, plus cloud brightness that changes with the storm.
  6. hypothesis Large RGBA PNGs drawn through SVG <image> (dock 2172×724, candle boat 1774×887, adult, child: about 25 MB decoded) and resampled under the 1.4× camera zoom.
  7. hypothesis Typewriter slicing re-lays out text on every frame while copy types. The window is short.

Profiling plan (bounded, physical iPhone)

  1. Use an older supported phone (such as an iPhone 12 or SE 3) plus Safari Web Inspector over cable, with the Timelines tab (Rendering Frames, JavaScript, Memory) and the Layers tab.
  2. Record one 29-screen scroll and one storm scrub. Note the share of frames over 16.7ms, peak memory, and layer count and size.
  3. Repeat with one change at a time: star opacity on the layer, grain off, waves paused. Keep a change only if it measurably helps.
  4. Do one pass in Low Power Mode and one with the 120Hz flag on. The acceptance bar is "usable at 30fps".
  5. Only if React time dominates: write transforms directly rather than via state. That is a later step, not part of this change.
